# Agent Operating Rules

This file is the single source of rules for coding agents (Claude Code, Codex, etc.) and human contributors working in this repository.
`CLAUDE.md` contains only the single line `@AGENTS.md`; do not write separate rules there. Read this file in full before changing a score, the converter, or a published PDF.
For user-facing documentation, see [README.md](README.md) (Japanese; translations: [README.zh-CN.md](README.zh-CN.md), [README.en.md](README.en.md)).

## Language

- Communicate with the user in the language the user writes in.
- Repository documents are written in Japanese by default. Every document also has a Simplified Chinese (`*.zh-CN.md`) and an English (`*.en.md`) translation next to it (for example `README.md`, `README.zh-CN.md`, `README.en.md`). The three versions must have the same content and structure. Any edit to a document updates all three versions in the same change.
- `AGENTS.md` is the exception: it is English only and has no translations.
- Program output (error messages, warnings, processing summaries, validation results, `--help`) is English only: no Chinese or Japanese text in messages. Japanese appears only as score content: the labels printed on the PDF (作詞, ドラム採譜, 凡例, ドラム譜), song credits, and the Japanese instrument names (`name_ja`).

## Repository purpose

- This is an extensible collection of **user-made drum scores**, plus a reproducible "drum MIDI → MusicXML + PDF" toolchain. It is not specific to any one song.
- Score material lives in `scores/<stable ASCII slug>/`; reusable software lives in `scripts/`, `configs/`, `tests/`, `docs/`, and `templates/`.
- Do not claim that a score is official or that it matches the original recording note for note. The source MIDI may contain the transcriber's reconstruction or arrangement.

## Sources and per-song files

- `source.mid`: the original MIDI supplied by the user. It is **immutable**. Never overwrite it with a quantized, shifted, or channel-remapped version.
- Derived MIDI files (such as `gm-channel10.mid`) are allowed, but the song README must state which file they were derived from and with which command.
- `metadata.yaml`: credits, drum map, track selection, pickup, quantization, and other settings. The fields are described in `docs/metadata.md` (Japanese; also `docs/metadata.zh-CN.md` and `docs/metadata.en.md`). Start a new song by copying `templates/metadata.yaml`.
- `score.musicxml`: the editable interchange format. `score.pdf`: the manually checked printable result. Both are generated by `scripts/build_score.py`.
- `README.md` (with its `.zh-CN.md` and `.en.md` translations): the song's source chain, generation commands, transcription notes, and copyright notes.
- When regenerating, keep the credits and remarks in the metadata. Do not overwrite a committed `score.musicxml` / `score.pdf` with new output without checking it.

## Pipeline

```text
source.mid + metadata.yaml
  └─ score_core.py      track selection → drum map → grace note/repeat detection → per-beat quantization (straight/triplet) → bar splitting
                        → per-voice durations, rests, beams (the only place that infers rhythm)
       ├─ midi_to_musicxml.py   → score.musicxml (MusicXML 4.0)
       └─ midi_to_musixtex.py   → MusiXTeX source (ASCII only)
            └─ render_score.py
                 1. musixtex -d typesets the staff (legend noteheads are typeset as a small staff and cropped)
                 2. gs -dNoOutputFonts converts every music glyph to vector paths
                 3. XeLaTeX + xeCJK + pdfpages compose the page: title block, legend text, headers, and page numbers are real text (Noto Sans CJK JP subset)
                 4. pdf_tounicode.py fixes ToUnicode from ActualText so that copying yields the correct characters
  └─ validate_score.py  validates the MusicXML and the PDF
```

- The two writers only translate the result of `score_core`; neither infers rhythm on its own. To change notation logic, change `score_core.py` and check both outputs.
- Do not fake a score with drawing primitives; the MusicXML must contain real notes, voices, and beams.
- When the input cannot be notated faithfully (unmapped notes, unsupported time signatures, 32nd notes or quintuplets, etc.), the converter must fail with an error that explains how to fix it. It must never silently drop notes or guess. New support requires changes to both the converter and the tests.
- Instrument position, notehead, and Japanese name are defined only in `configs/instruments.yaml`; the mapping from note numbers to instruments is defined only in `configs/drum-maps/*.yaml` and in each song's `note_map`. See `docs/drum-maps.md` (Japanese; also `docs/drum-maps.zh-CN.md` and `docs/drum-maps.en.md`).

## Verification duties

After changing the converter, configuration, or a score, complete the following before delivering:

1. `python3 -m pytest -q tests` (do not put the test sandbox on a volatile directory; use `--basetemp` to choose one). When `MUSICXML_XSD` is set, the XSD validation tests run; when `PDFJS_TEXT` is set (a pdf.js text-extraction script: `node script file.pdf` prints `--- page N` per page followed by the text fragments joined with `|`) and `node` is available, the text copied by pdf.js is also checked. When these are unset the tests are skipped, and the PDF tests are skipped when there is no TeX environment.
2. For each affected song, run `python3 scripts/build_score.py <midi> --metadata <yaml> --out-dir build/<slug>`. The exit code must be 0 (1 means validation failed; 2 means an input or environment problem). Set `MUSICXML_XSD` to the MusicXML 4.0 `musicxml.xsd` (requires lxml) so that validation includes the XSD schema check.
   The validation in `build_score.py` covers: bar count, time signatures, and pickup; the duration sum of each voice in each bar; the number of times each MIDI note is notated; beam levels; note-for-note agreement between the MusicXML and a fresh re-conversion; the PDF being A4, with vector music and no bitmaps, all fonts embedded with ToUnicode, and the copyable text of each page (extracted by ActualText and by ToUnicode alone) equal to the title block / legend / header / page number / copyright line.
   Comparison is done after NFC normalization with all whitespace removed, so spaces and line breaks must be checked in step 4.
3. Render the PDF to images (for example `pdftoppm -r 100 -png`) and inspect them by eye: at least the first page (title block, legend), the densest page, a middle page, and the last page. Look especially at notehead shapes, open/closed mark positions, beam counts, triplet numbers, grace notes, rests, time signature changes, line and page breaks, and any missing characters or substituted glyphs.
4. Optional: extract text with `pdftotext` and pdf.js (Firefox's PDF engine, i.e. the `PDFJS_TEXT` test) and confirm that the copied credits match the metadata character for character. No extra space should appear between Han characters and Latin letters; half-width spaces written in the metadata should be kept, except a half-width space after full-width punctuation. A full-width space (U+3000) is copied as a half-width space by both tools, which is normal.
5. State whether the change affects the score content or only the layout.

## Notation conventions summary

See `docs/notation-conventions.md` for details (Japanese; also `docs/notation-conventions.zh-CN.md` and `docs/notation-conventions.en.md`).

- One five-line staff with a percussion clef. Hands (snare, toms, cymbals, hi-hat, auxiliary percussion) are the upper voice with stems up; feet (bass drum, hi-hat pedal) are the lower voice with stems down.
- Drums use filled oval noteheads; cymbals and hi-hat use x noteheads. Open is marked with a small circle ○, half-open with ⊖, and closed with ＋. The mark is printed above the actual notehead (3 positions high for hands, 2 for feet), and the score matches the legend.
- Noteheads a second apart in the same voice are printed on both sides of the stem; marks and ghost parentheses move with the notehead. When a hand and a foot notehead are within a second of each other they are offset horizontally, and a notice is given when both voices carry beams and cannot be offset.
- Stems of x and circled-x noteheads start from the end of an arm of the x (the upper right end when stem up, the lower left end when stem down).
- Beams are grouped by beat and never cross a beat: one beam for 8th notes, two for 16ths. An isolated 16th inside a beam group uses a short beam (hook); a single note outside any beam group uses a flag. Triplets are labeled 3 and 16th sextuplets are labeled 6: when the whole group has one beam the number is printed on the beam; when the group contains a rest or a flag the number is printed above (hands) or below (feet) the group. In MusicXML these are `bracket="no"` and `bracket="yes"` respectively. Triplets are decided per beat and per voice; the rule is in `docs/metadata.md`.
- A line normally holds at most 4 bars; a very short last line is merged into the previous line (up to 5 bars).
- The pickup bar is numbered 0 and prints its own time signature; time signature changes can only occur at barlines.
- The hand and foot voices each fill every beat (identically in PDF and MusicXML): rests in the hand voice sit high and rests in the foot voice sit low, and rests that occur in both voices at the same time with the same length are merged into one centered rest. Consecutive empty bars are merged into a multi-measure rest.
- The legend is not printed by default; it is printed with `legend: true` or `--legend` and lists only the instruments actually used. The last line of the title block shows only `BPM <tempo>`.
- Left/right hand order cannot be inferred from MIDI; do not add sticking to the score.

## Commit rules

- Do not commit anything under `build/`, TeX intermediate files, logs, temporary PNGs, font files (including font subsets), credentials, or unrelated files. Fonts come only from the system install (`fonts-noto-cjk`).
- When changing the shared converter, keep the change small and focused; do not commit newly generated scores until the tests and render checks pass.
- Documentation must match the current code; when behavior changes, update the documentation too, in all three languages (see Language).
